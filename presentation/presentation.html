// PAPEL E EVOLUÇÃO

O que um QA faz?

A evolução de 'testador manual de telas' para Engenheiro de Qualidade de Software (QE).

🔄 A Transformação do QA

  • Da verificação manual à Engenharia de Qualidade: O foco mudou de encontrar erros no fim do ciclo para garantir qualidade em todas as etapas.
  • Escopo Completo: Requisitos funcionais, performance, resiliência, usabilidade e segurança da informação.
  • Shift-Left Testing: Testar o quanto antes, questionando regras de negócio e validações antes mesmo de o código ir para produção.

🎯 Além do Navegador

  • O QA moderno não clica apenas em botões na tela: ele valida contratos de APIs, regras de autorização e integridade de dados.
  • Se o frontend oculta um botão, a API ainda aceita a requisição?
  • Testes de caminhos negativos, abuso de parâmetros e cenários imprevistos.
// PILAR CRÍTICO

Teste de Segurança em APIs

Por que segurança de APIs é responsabilidade direta dos times de Qualidade e Desenvolvimento?

🌐 Tráfego Moderno

Mais de 80% do tráfego web atual trafega exclusivamente por REST APIs consumidas por SPAs, apps mobile e microsserviços.

⚠️ O Perigo Silencioso

Falhas de autorização NÃO quebram o sistema! Não geram erro 500, crash no log nem alertas visuais na interface.

🎯 200 OK Ilusório

Se um invasor altera o preço de um produto de R$ 15.000 para R$ 1,00, a API responde contente: 200 OK - Pedido Criado com Sucesso.

💡 Missão do QA: Simular comportamento adverso. Testar o que o usuário não deveria conseguir fazer através do OWASP API Security Top 10.

// ESTRATÉGIA DE COBERTURA

Camadas de Teste para APIs

Como distribuir os testes para garantir velocidade, precisão e segurança no pipeline.

Camada 1

🧪 Unitários

Validam funções puras isoladas (ex: cálculo de descontos, validação de hashes de senha e regras matemáticas).

Camada 2

🔌 Integração

Validam a integração de middlewares de autenticação, injeção de dependências e acesso ao banco de dados.

Camada 3

🛡️ API & Segurança

Testes de contrato e Live Hacking (BFLA, BOLA/IDOR, adulteração de parâmetros e impersonation de contas).

Camada 4

🚀 E2E

Fluxos completos ponta a ponta navegando pela UI web e mobile até o fechamento de pedidos.

// FUNDAMENTOS HTTP

Entendendo o Conceito de REST API

A base das comunicações distribuídas: arquitetura cliente-servidor e protocolo HTTP.

📡 Métodos HTTP Semânticos

  • GET Leitura / Consulta: Recupera dados sem causar efeitos colaterais.
  • POST Criação: Envia dados para criar um novo registro no servidor.
  • PUT / PATCH Atualização: Modifica recursos (total ou parcial). Alvo frequente de BOLA.
  • DELETE Exclusão: Remove um recurso. Deve sempre validar o proprietário.
⚡ Stateless: Cada requisição carrega credenciais completas (Token JWT) para ser autorizada de forma independente.

🚦 Códigos de Status que o QA Audita

  • 200 / 201 Sucesso: Operação realizada com conformidade e resposta correta.
  • 401 Unauthorized: O usuário NÃO está autenticado (falta token ou token expirado/inválido).
  • 403 Forbidden: O usuário ESTÁ autenticado, mas NÃO TEM PERMISSÃO para este recurso específico.
  • 404 Not Found: Recurso não existe ou ID mascarado por segurança.
🎯 Regra de Ouro: Se a API responder 200 OK para um usuário sem direito de acesso, temos uma vulnerabilidade grave!

Token: Desmistificando o JWT

O maior mito de segurança do mercado: JWT NÃO É CRIPTOGRAFIA!

🔴 Header (Vermelho)

Metadados da assinatura: especifica o algoritmo criptográfico (ex: HS256, RS256) e tipo de token.

🟣 Payload (Rosa)

Claims do usuário (ID, login, perfil). Codificado apenas em Base64URL. Qualquer pessoa no mundo consegue decodificar e ler!

🟠 Assinatura (Laranja)

Garante que o conteúdo não foi alterado. Perigo: Se a chave privada for fraca (ex: secret123), o invasor forja tokens de ADMIN em segundos.

// TOP VULNERABILIDADES OWASP

BFLA & BOLA: As Falhas Mais Perigosas

As causas mais comuns de vazamento massivo de dados em plataformas modernas.

🎯 BFLA (Quebra de Nível de Função)

OWASP API5:2023: A API checa se o usuário está logado, mas esquece de validar o papel (Role).

// Vulnerável: só checa se tem token!
app.get("/api/v1/admin/financials", authenticate, (req, res) => {
  res.json(db.getFinancialMetrics()); // Cliente comum vê receita!
});

💥 BOLA (Quebra em Nível de Objeto)

OWASP API1:2023 (#1 do mundo): Confiança cega no ID passado na rota/URL sem checar dono.

// Vulnerável: Maria edita produto do concorrente João!
app.put("/api/v1/products/:id/price", authenticate, (req, res) => {
  Product.update({ price: req.body.price }, { where: { id: req.params.id } });
});

// CONCLUSÃO & APRENDIZADOS

Considerações Finais

3 lições fundamentais que todo engenheiro de software e QA deve levar para a carreira:

1. Token ≠ Permissão

Saber quem é o usuário é só metade da segurança. Saber o que ele tem direito de acessar e modificar é o que protege o negócio.

2. Valide o Dono Sempre

Nunca execute updates ou deletes baseando-se unicamente no ID da URL. Amarre a consulta: WHERE id = ? AND owner_id = ?.

3. Qualidade & Segurança

Segurança não é assunto exclusivo de hackers ou pentest no final do ano: começa na modelagem da API e nos testes contínuos do QA.
